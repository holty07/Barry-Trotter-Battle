# 05 — Client and UI

## The contract

The client renders `PlayerView` and sends `Action`s. It contains no rules. Specifically:

- **The UI never decides what choices exist.** Every prompt is rendered from `view.pending`. If
  the client is constructing a "choose a hero" dialog from its own logic, that logic is a second
  implementation of the rules and it will drift.
- **Legality is the server's call.** The client may grey out a card it believes is unaffordable
  as a hint, but it always sends the action and always accepts a `rejected` reply gracefully.
- **Card text is display-only.** `view` carries `name`, `text`, cost and art reference for cards
  the player can see. The client never parses `text`.

## Screens

1. **Home** — create a room, or join with a code. Name field. That's all.
2. **Lobby** — room code (big, copyable), seat list, hero pick per seat, year select, hand
   visibility toggle, start button. Host is whoever created the room.
3. **Table** — the game.
4. **End** — won/lost, the game log, "play the next year with the same seats".

Narrow screens (iPad portrait, phone): the threat bands become a swipeable pair of panes, the
location spine and your own dock stay pinned. Your hand and the pending prompt must never require
scrolling to find.

## The one thing that must be unmissable

Whose turn it is, and whether the game is waiting on *you*. In a remote co-op, the failure mode is
four people staring at a board waiting for each other. When `view.pending.seat === you`, the
prompt takes over the lower third of the screen as a sheet — not a centred modal that could be
mistaken for a notification — and everyone else's UI shows a clear "waiting for Ron to discard a
card" state in the same position. Same slot, same words, so it's learnable.

## Design direction (proposal — tell me if you want a different one)

The subject is a rising-threat co-op: the interesting visual fact is that the board gets worse
over time and the players are pushing back. Lean on that instead of decorating with wizarding
motifs — which you also can't ship, since the trademarked look and the art are off the table.

- **Palette** (5 tokens): `slate-950 #10131A` table surface, `slate-800 #232A36` panels,
  `bone #EDE8DF` card faces, `signal #C1392B` threat and control, `brass #B08843` resources and
  acquisition. One accent for danger, one for gain, nothing else.
- **The bold move, spent once:** the location spine at the top is the only element that changes
  colour over the course of a game. Control tokens fill it left to right in `signal`, and as it
  fills, the page background shifts one or two steps darker. Nothing else animates on its own.
  It should be possible to glance at a screenshot and know how badly the game is going.
- **Type:** two families, clearly distinct. A high-contrast transitional serif for card names and
  headings (Newsreader or Petrona), a tightly-set grotesque with tabular figures for all numbers
  and UI chrome (Archivo or Inter Tight). Tabular figures matter — health and attack values
  change constantly and shouldn't jitter.
- **Cards** are the densest information on screen, so give them the most contrast: bone face,
  dark text, cost and type as structural marks (a corner rule for type, cost as a filled disc),
  not as labels. No card should need a caption to identify its type.
- **Motion** only in response to a state change, and only where it explains something: a card
  moving from market to discard, damage landing on a villain, a control token appearing. No
  entrance animations, no hover lifts. Respect `prefers-reduced-motion`.
- **Copy:** sentence case, active voice, plain verbs. Buttons say what happens ("Assign 3 attack",
  "End turn"). The same action keeps the same name everywhere. Empty and error states say what to
  do next in the interface's voice, not an apology.

Avoid: cream-and-serif parchment (the current AI-design house style, and it fights legibility on
a dense board), gradient washes, identical rounded cards for everything regardless of hierarchy,
and all-caps eyebrow labels above panels.

## Implementation notes

- One React context for the socket connection and the current view. Components read the view;
  they don't fetch.
- Derive everything renderable from `view` with plain selector functions, memoised. No client
  state duplicating server state — the only local state is UI state (which panel is open, what's
  hovered, the pending prompt's draft selection).
- Reconnect handling belongs in the socket provider, with a visible "reconnecting" banner and
  automatic `resync`. Test it by throttling to offline in devtools mid-turn.
- Accessibility floor: keyboard-operable card selection and prompts, visible focus, ARIA live
  region announcing turn changes and Dark Arts reveals. This isn't ceremony — it's how you'll
  play on a laptop with no mouse.
